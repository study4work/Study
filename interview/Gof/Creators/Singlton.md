### Singleton (Одиночка)
это порождающий паттерн проектирования, который гарантирует, что у класса есть только один экземпляр, 
и предоставляет к нему глобальную точку доступа.

Три базовых правила для создания классического синглтона:
1. Закрытый (private) конструктор, чтобы никто не мог создать объект через new.
2. Статическая переменная, хранящая единственный экземпляр класса.
3. Публичный статический метод (обычно getInstance()), который возвращает этот экземпляр.
Где применяется: логирование, кэширование, пулы потоков, настройки конфигурации, драйверы баз данных.

## Как реализовать потокобезопасный Singleton
В многопоточной среде наивная реализация (просто проверка if (instance == null)) сломается: 
два потока могут одновременно пройти проверку и создать два объекта.

#### Способ А: Enum
Это самый надежный способ. Он потокобезопасен "из коробки", защищает от создания новых экземпляров 
через Reflection и автоматически решает проблемы с сериализацией.
```java
public enum Singleton {
    INSTANCE;
    
    public void doSomething() {
        // бизнес-логика
    }
}
```

#### Способ Б: Инициализация через статический блок
Объект создается сразу при загрузке класса. Потокобезопасность гарантируется механизмом загрузки классов (ClassLoader) в Java.
```java
public class Singleton {
    // Создается при загрузке класса, потокобезопасно
    private static final Singleton INSTANCE = new Singleton();

    private Singleton() {}

    public static Singleton getInstance() {
        return INSTANCE;
    }
}
```
Минус: Объект создается даже если он никогда не понадобится (нет ленивой инициализации).

#### Способ В: Bill Pugh Singleton (Ленивая инициализация через внутренний класс)
Использует механизмы ClassLoader. Внутренний класс загружается только при первом вызове getInstance().
```java
public class Singleton {
    private Singleton() {}

    // Внутренний статический класс (Holder)
    private static class SingletonHolder {
        private static final Singleton INSTANCE = new Singleton();
    }

    public static Singleton getInstance() {
        return SingletonHolder.INSTANCE;
    }
}
```

## Что такое Double-Checked Locking
это идиома, используемая для реализации ленивой (lazy) и потокобезопасной инициализации синглтона с минимальными накладными расходами на производительность.
Суть: Мы хотим избежать использования ключевого слова synchronized на каждом вызове getInstance(), так как это замедляет работу. 
Синхронизация нужна только при первом создании объекта.
```java
public class Singleton {
    // Ключевое слово volatile ОБЯЗАТЕЛЬНО!
    private static volatile Singleton instance; 

    private Singleton() {}

    public static Singleton getInstance() {
        // Первая проверка (без синхронизации - быстро)
        if (instance == null) { 
            synchronized (Singleton.class) { // Блокировка
                // Вторая проверка (на случай, если два потока прошли первую проверку одновременно)
                if (instance == null) { 
                    instance = new Singleton();
                }
            }
        }
        return instance;
    }
}
```
**Зачем нужен volatile**?
Без volatile в Java (до версии 5.0 и даже после, если не использовать volatile) возможна ситуация переупорядочивания инструкций (instruction reordering) на уровне процессора/JVM.
Процесс создания объекта (new Singleton()) состоит из трех шагов:
1. Выделение памяти.
2. Инициализация объекта (вызов конструктора).
3. Присваивание ссылки переменной instance.
JVM может поменять шаги 2 и 3 местами. В итоге поток А выделит память, присвоит ссылку переменной instance (она уже не null!), но еще не вызовет конструктор. Поток Б зайдет в метод, увидит, что instance != null, и вернет недоинициализированный (сырой) объект, что приведет к NullPointerException в рантайме.
Модификатор volatile запрещает такое переупорядочивание.

## Каковы проблемы синглтона
* **Глобальное состояние (Global State):**
Синглтон по сути является глобальной переменной. Любой класс в системе может получить к нему доступ и изменить его состояние. Это делает код непредсказуемым и усложняет отладку.
Сложность модульного тестирования:
Поскольку синглтон хранит состояние между тестами, тесты могут влиять друг на друга (один тест сломал состояние, следующий упал). Кроме того, его очень сложно подменить на Mock-объект при написании Unit-тестов.
* **Скрытые зависимости:**
Когда класс использует синглтон внутри своих методов (через Singleton.getInstance()), это не видно из сигнатуры класса или конструктора. Это нарушает принцип явных зависимостей (Dependency Injection).
* **Нарушение принципа единственной ответственности (SRP):**
Класс отвечает не только за свою бизнес-логику, но и за управление своим жизненным циклом (создание и хранение единственного экземпляра).
* **Проблемы с Reflection и Serialization (для классических реализаций):**
Reflection: С помощью Java Reflection API можно вызвать private конструктор и создать второй экземпляр синглтона.
Serialization: При десериализации объекта Java по умолчанию создает новый экземпляр класса. 
Чтобы синглтон остался синглтоном после сериализации, нужно вручную реализовывать метод readResolve(). (Примечание: Enum синглтон лишен этих проблем).
* **Проблемы в многопоточности и наследовании:**
Как мы видели, легко написать синглтон, который будет работать некорректно в многопоточной среде. Также синглтоны плохо наследуются.
