# Алгоритмы Garbage Collection в Java

## Введение

В Java существует несколько алгоритмов сборщика мусора (GC), каждый из которых оптимизирован под разные цели.

Глобально все GC делятся по двум главным метрикам:

1. **Throughput (Пропускная способность)** — какой процент времени приложение тратит на полезную работу, а не на сборку мусора
2. **Latency (Задержка / Pause Time)** — насколько долго приложение "замораживается" (Stop-The-World, STW) во время сборки мусора

---

## 1. Serial GC (Последовательный)

**Флаг:** `-XX:+UseSerialGC`

### Как работает
Использует **один поток** для всей работы. При запуске GC полностью останавливает все потоки приложения (Stop-The-World). Использует алгоритм *Mark-Sweep-Compact* (пометить, очистить, уплотнить).

### Плюсы
- ✅ Минимальные накладные расходы (overhead)
- ✅ Простота
- ✅ Не требует много ядер CPU

### Минусы
- ❌ Долгие паузы при большом объеме памяти

### Когда использовать
- Маленькие приложения
- Десктопные утилиты
- Встроенные системы (embedded)
- Среды с 1 ядром CPU
- Очень маленький heap (до 100-200 МБ)

---

## 2. Parallel GC (Throughput GC)

**Флаг:** `-XX:+UseParallelGC`

### Как работает
Многопоточная версия Serial GC. Использует несколько потоков для ускорения сборки мусора в Young и Old поколениях. Полностью останавливает приложение (STW) во время работы.

### Плюсы
- ✅ Максимальная пропускная способность (throughput)
- ✅ Эффективно использует многоядерные процессоры

### Минусы
- ❌ Непредсказуемые и потенциально долгие паузы (Stop-The-World)
- ❌ Приоритет отдается скорости очистки, а не времени отклика

### Когда использовать
- Фоновые задачи
- Batch-обработка данных
- Научные вычисления
- Где важно сделать как можно больше работы за единицу времени
- Миллисекундные задержки не важны

*Был сборщиком по умолчанию в Java 8*

---

## 3. CMS (Concurrent Mark Sweep)

**Флаг:** `-XX:+UseConcMarkSweepGC`

### Как работает
Пытается выполнять большую часть работы (пометку и очистку) **параллельно** с работающим приложением, чтобы минимизировать паузы. Работает только с Old Generation (для Young используется Parallel). Не делает уплотнение (compaction) по умолчанию, что ведет к фрагментации памяти.

### Плюсы
- ✅ Короткие паузы (низкая latency)

### Минусы
- ❌ Высокая нагрузка на CPU
- ❌ Фрагментация памяти
- ❌ Риск "Concurrent Mode Failure" (если приложение выделяет память быстрее, чем CMS успевает чистить, происходит fallback в медленный Serial GC)

### Статус
**⚠️ Устарел в Java 9, полностью удален в Java 14.** Упоминается только для понимания истории, его место занял G1 GC.

---

## 4. G1 GC (Garbage-First)

**Флаг:** `-XX:+UseG1GC`

### Как работает
Сборщик **по умолчанию** начиная с Java 9.

Вместо жесткого деления на физические Young и Old блоки, он делит весь heap на множество равных **регионов** (regions, обычно по 1-32 МБ).

GC оценивает, сколько "мусора" находится в каждом регионе, и в первую очередь очищает те регионы, где мусора больше всего (отсюда название *Garbage-First*). Позволяет задать целевое время паузы (например, 200 мс), и GC подстраивается под него.

### Плюсы
- ✅ Предсказуемые и настраиваемые паузы
- ✅ Хороший баланс между throughput и latency
- ✅ Автоматически уплотняет память (борется с фрагментацией)

### Минусы
- ⚠️ Выше накладные расходы на CPU по сравнению с Parallel GC

### Когда использовать
- Универсальный выбор для большинства современных приложений
- Особенно с heap от 4 ГБ до 32 ГБ
- Где важны стабильные задержки (веб-сервисы, микросервисы)

---

## 5. ZGC (Z Garbage Collector)

**Флаг:** `-XX:+UseZGC`

### Как работает
Современный низколатентный сборщик (стал production-ready в Java 15, значительно улучшен в Java 21). Работает **полностью параллельно** с приложением. Использует продвинутые техники (цветные указатели / pointer coloring и load barriers), чтобы перемещать объекты в памяти *без остановки потоков приложения*.

### Плюсы
- ✅ Экстремально низкие паузы (менее **1 миллисекунды**)
- ✅ Паузы **не зависят от размера heap** (хоть 100 МБ, хоть 16 ТБ)

### Минусы
- ⚠️ Снижает общую пропускную способность (throughput) на 5-15% из-за постоянных вычислений барьеров памяти
- ⚠️ Требует больше оперативной памяти

### Когда использовать
- Приложения, критичные к задержкам (High-Frequency Trading, онлайн-игры, real-time аналитика)
- Приложения с огромным объемом памяти (сотни гигабайт), где паузы других GC были бы недопустимо долгими

---

## 6. Shenandoah GC

**Флаг:** `-XX:+UseShenandoahGC`

### Как работает
Разработан компанией Red Hat (появился в OpenJDK 12). Идеологически очень похож на ZGC: тоже стремится к паузам менее 10 мс независимо от размера кучи, используя техники "evacuation" (эвакуации) объектов параллельно с работой приложения.

### Плюсы
- ✅ Сверхнизкие паузы
- ✅ Хорошая производительность на больших кучах

### Минусы
- ⚠️ Как и ZGC, немного снижает общий throughput

### Когда использовать
- Альтернатива ZGC
- Особенно популярна в экосистеме Red Hat / OpenShift

## Сводная таблица алгоритмов GC

| Алгоритм | Главная цель | Паузы (STW) | Размер Heap | Статус в современной Java |
| :--- | :--- | :--- | :--- | :--- |
| **Serial** | Мин. overhead | Долгие | Очень маленький (< 200 МБ) | Актуален для embedded |
| **Parallel** | Макс. Throughput | Долгие, непредсказуемые | Любой (обычно до 8-16 ГБ) | Актуален для batch-задач |
| **CMS** | Низкая Latency | Короткие | Средний | ❌ Удален (Java 14+) |
| **G1** | Баланс | Предсказуемые, настраиваемые (< 200 мс) | Средний и большой (4 - 32 ГБ) | ✅ **По умолчанию** (Java 9+) |
| **ZGC** | Ультра-низкая Latency | < 1 мс (не зависит от размера) | Огромный (до 16 ТБ) | ✅ Рекомендован для real-time |
| **Shenandoah** | Ультра-низкая Latency | < 10 мс (не зависит от размера) | Огромный | ✅ Альтернатива ZGC |

## Как выбрать GC для своего проекта?

### Правило 1: Не выбирайте ничего специально
Если у вас нет проблем, оставьте **G1 GC** (он по умолчанию в Java 11/17/21). Он отлично справляется с 95% задач.

### Правило 2: Фоновая обработка данных
Если у вас **фоновая обработка данных** (cron-джобы, ETL), и вам плевать на паузы, но важна скорость завершения — включите **Parallel GC**.

```bash
java -XX:+UseParallelGC -jar myapp.jar
