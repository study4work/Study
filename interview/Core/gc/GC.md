# Алгоритмы Garbage Collection в Java

## Введение

В Java существует несколько алгоритмов сборщика мусора (GC), каждый из которых оптимизирован под разные цели.

Глобально все GC делятся по двум главным метрикам:

1. **Throughput (Пропускная способность)** — какой процент времени приложение тратит на полезную работу, а не на сборку мусора
2. **Latency (Задержка / Pause Time)** — насколько долго приложение "замораживается" (Stop-The-World, STW) во время сборки мусора

1. Пропускная способность (Throughput)
   Что это: Это процент времени, которое ваше приложение тратит на полезную работу (выполнение бизнес-логики, обработку запросов), а не на сборку мусора.
2. Время отклика / Задержка (Latency)
   Что это: Это максимальное время, на которое приложение замораживается (пауза Stop-The-World) или замедляется в ответ на конкретный запрос пользователя.

---

## 1. Serial GC (Последовательный)

**Флаг:** `-XX:+UseSerialGC`

### Как работает
Использует **один поток** для всей работы. При запуске GC полностью останавливает все потоки приложения (Stop-The-World). Использует поколенческую гипотезу.
1. Для Молодого поколения (Young Generation) — Копирующий алгоритм (Copying / Mark-Copy)
2. Для Старого поколения (Old Generation) — Mark-Sweep-Compact (Отслеживание-Очистка-Уплотнение)

### Плюсы
- ✅ Минимальные накладные расходы (overhead)
- ✅ Простота
- ✅ Не требует много ядер CPU

### Минусы
- ❌ Долгие паузы при большом объеме памяти

### Когда использовать
- Маленькие приложения
- Десктопные утилиты
- Встроенные системы (embedded)
- Среды с 1 ядром CPU
- Очень маленький heap (до 100-200 МБ)

---

## 2. Parallel GC (Throughput GC)

**Флаг:** `-XX:+UseParallelGC`

### Как работает
Многопоточная версия Serial GC. Использует несколько потоков для ускорения сборки мусора в Young и Old поколениях. Полностью останавливает приложение (STW) во время работы.

### Плюсы
- ✅ Максимальная пропускная способность (throughput)
- ✅ Эффективно использует многоядерные процессоры

### Минусы
- ❌ Непредсказуемые и потенциально долгие паузы (Stop-The-World)
- ❌ Приоритет отдается скорости очистки, а не времени отклика

### Когда использовать
- Фоновые задачи
- Batch-обработка данных
- Научные вычисления
- Где важно сделать как можно больше работы за единицу времени
- Миллисекундные задержки не важны

*Был сборщиком по умолчанию в Java 8*

---

## 3. CMS (Concurrent Mark Sweep)

**Флаг:** `-XX:+UseConcMarkSweepGC`

### Как работает
Главная цель CMS — минимизировать паузы (low latency) Работает только с Old Generation (для Young используется Parallel). Не делает уплотнение (compaction) по умолчанию, что ведет к фрагментации памяти.

### Плюсы
- ✅ Короткие паузы (низкая latency)

### Минусы
- ❌ Высокая нагрузка на CPU
- ❌ Фрагментация памяти
- ❌ Риск "Concurrent Mode Failure" (если приложение выделяет память быстрее, чем CMS успевает чистить, происходит fallback в медленный Serial GC)

### Статус
**⚠️ Устарел в Java 9, полностью удален в Java 14.** Упоминается только для понимания истории, его место занял G1 GC.

---

## 4. G1 GC (Garbage-First)

**Флаг:** `-XX:+UseG1GC`

### Как работает
Он был создан, чтобы взять лучшее от CMS (низкие паузы) и лучшее от Parallel GC (высокая пропускная способность), при этом решив главную проблему CMS — фрагментацию памяти.

Все предыдущие GC (Serial, Parallel, CMS) делили кучу на две большие непрерывные области: Young Gen и Old Gen. G1 полностью отказывается от этой модели.
Вместо этого G1 разбивает всю кучу на множество маленьких одинаковых регионов (обычно от 1 до 32 МБ каждый). Для кучи в 8 ГБ это может быть ~2000 регионов.

Каждый регион может динамически менять свою роль. Один и тот же регион может быть Eden сейчас, а через цикл GC стать Old или Free. Это дает G1 невероятную гибкость.

Для регионов типа eden G1 использует алгоритм копирования (как Serial/Parallel GC для Young Gen), но копирует не в фиксированную зону, а в любые свободные регионы. Это автоматически устраняет фрагментацию — объекты лежат плотно в новых регионах.

Ключевая особенность можно задать время пауз STW

### Плюсы
- ✅ Предсказуемые и настраиваемые паузы
- ✅ Хороший баланс между throughput и latency
- ✅ Автоматически уплотняет память (борется с фрагментацией)

### Минусы
- ⚠️ Выше накладные расходы на CPU по сравнению с Parallel GC

### Когда использовать
- Универсальный выбор для большинства современных приложений
- Особенно с heap от 4 ГБ до 32 ГБ
- Где важны стабильные задержки (веб-сервисы, микросервисы)

## 5. ZGC (Z Garbage Collector)

**Флаг:** `-XX:+UseZGC`

### Как работает
Современный низколатентный сборщик (стал production-ready в Java 15, значительно улучшен в Java 21). Работает **полностью параллельно** с приложением.
ZGC хранит метаданные прямо в указателе (в ссылке на объект).
Как это работает:
В 64-битной системе адрес объекта занимает не все 64 бита. Например, при куче до 4 ТБ используется только 42 бита адреса.
Оставшиеся свободные биты (обычно 4-8 бит) ZGC использует для хранения цветовых меток (color bits).
```java
[ 42 бита: адрес объекта ][ 4 бита: цветовые метки ][ 18 бит: не используются ]
```

### Плюсы
- ✅ Экстремально низкие паузы (менее **1 миллисекунды**)
- ✅ Паузы **не зависят от размера heap** (хоть 100 МБ, хоть 16 ТБ)

### Минусы
- ⚠️ Снижает общую пропускную способность (throughput) на 5-15% из-за постоянных вычислений барьеров памяти
- ⚠️ Требует больше оперативной памяти

### Когда использовать
- Приложения, критичные к задержкам (High-Frequency Trading, онлайн-игры, real-time аналитика)
- Приложения с огромным объемом памяти (сотни гигабайт), где паузы других GC были бы недопустимо долгими

## 6. Shenandoah GC

**Флаг:** `-XX:+UseShenandoahGC`

### Как работает
Чтобы перемещать объекты параллельно с работой приложения (Concurrent Evacuation), сборщику нужно, чтобы приложение, обратившись к старому адресу объекта, мгновенно узнало его новый адрес.
ZGC решает это через цветные указатели (хакинг битов в адресе).  
Shenandoah решает это более классическим, но гениальным способом — через Указатели Брукса.  
**Как это работает:**  
В заголовок каждого объекта в куче добавляется одно дополнительное поле — forwarding pointer (указатель пересылки).
Пока объект находится на своем месте, этот указатель ссылается на самого себя.
Когда GC решает переместить объект в новое место (Evacuation), он:
Копирует объект в новую область памяти.
В старом месте объекта меняет его Brooks Pointer так, чтобы он указывал на новый адрес.
Когда поток приложения пытается прочитать или изменить этот объект по старому адресу, он натыкается на Read/Write Barrier (барьер).
Барьер проверяет Brooks Pointer: "Ага, этот указатель ведет не на самого себя, а на другой адрес. Значит, объект переехал". Приложение автоматически переходит по новому адресу.  
Плюс такого подхода: Не нужно "ломать" структуру 64-битных указателей (как в ZGC с цветными битами), что делает Shenandoah более портируемым на разные архитектуры (например, он легче портируется на 32-битные системы или ARM, хотя сейчас в основном используется на 64-бит x86/ARM).
Минус: Каждый объект в куче становится немного "тяжелее" (на 8 байт на 64-битной системе) из-за дополнительного поля в заголовке.

### Плюсы
- ✅ Сверхнизкие паузы
- ✅ Хорошая производительность на больших кучах

### Минусы
- ⚠️ Как и ZGC, немного снижает общий throughput

### Когда использовать
- Альтернатива ZGC
- Особенно популярна в экосистеме Red Hat / OpenShift

## Сводная таблица алгоритмов GC

| Алгоритм | Главная цель | Паузы (STW) | Размер Heap | Статус в современной Java |
| :--- | :--- | :--- | :--- | :--- |
| **Serial** | Мин. overhead | Долгие | Очень маленький (< 200 МБ) | Актуален для embedded |
| **Parallel** | Макс. Throughput | Долгие, непредсказуемые | Любой (обычно до 8-16 ГБ) | Актуален для batch-задач |
| **CMS** | Низкая Latency | Короткие | Средний | ❌ Удален (Java 14+) |
| **G1** | Баланс | Предсказуемые, настраиваемые (< 200 мс) | Средний и большой (4 - 32 ГБ) | ✅ **По умолчанию** (Java 9+) |
| **ZGC** | Ультра-низкая Latency | < 1 мс (не зависит от размера) | Огромный (до 16 ТБ) | ✅ Рекомендован для real-time |
| **Shenandoah** | Ультра-низкая Latency | < 10 мс (не зависит от размера) | Огромный | ✅ Альтернатива ZGC |

## Как выбрать GC для своего проекта?

### Правило 1: Не выбирайте ничего специально
Если у вас нет проблем, оставьте **G1 GC** (он по умолчанию в Java 11/17/21). Он отлично справляется с 95% задач.

### Правило 2: Фоновая обработка данных
Если у вас **фоновая обработка данных** (cron-джобы, ETL), и вам плевать на паузы, но важна скорость завершения — включите **Parallel GC**.

```bash
java -XX:+UseParallelGC -jar myapp.jar
