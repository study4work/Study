## Флаги памяти JVM
**-Xms<size>** — начальный и минимальный размер кучи. JVM выделяет столько при старте и не опускается ниже этого значения;  
**-Xmx<size>** — максимальный размер кучи. Выше этого потолка куча вырасти не может; при исчерпании — OutOfMemoryError: Java heap space.
На серверных приложениях распространён приём: -Xms и -Xmx выставляют равными. Причина — в устранении накладных расходов на рост кучи.

**-XX:+HeapDumpOnOutOfMemoryError** — при возникновении OutOfMemoryError JVM автоматически снимает heap dump (снимок всей кучи) в формате HPROF, прямо в момент падения. Это самый ценный снимок: он зафиксировал память ровно тогда, когда её не хватило.  
**-XX:HeapDumpPath** — куда положить файл. Можно указать каталог или имя файла; в имени допустим placeholder %p (подставляется PID). Без этого флага файл java_pid<pid>.hprof создаётся в рабочем каталоге процесса.  
Эти два флага — фактически обязательная гигиена для любого прод-сервиса: накладных расходов в обычной работе они не несут (дамп снимается только при OutOfMemoryError), а при аварии дают готовый материал для разбора.  
**-Xlog:gc*** - это текстовая летопись работы сборщика: когда запускалась сборка, сколько длилась пауза, сколько памяти освободила, каким было заполнение кучи до и после. Это первый, самый дешёвый источник данных о поведении памяти: он включается флагом и не требует ни подключения инструментов, ни снятия дампа.

Начиная с Java 9 GC-лог включают через унифицированную систему логирования JVM — флаг -Xlog:
```java
-Xlog:gc            # краткие сообщения о сборках
-Xlog:gc*           # подробно: все теги, связанные с GC, со всеми фазами
-Xlog:gc*:file=gc.log   # писать в файл gc.log, а не в консоль
```

**Что искать в GC-логе**  
1. Частота пауз. Как часто запускается сборка. Участившиеся Full GC (полные сборки, затрагивающие Old Generation) — тревожный признак: приложение всё чаще вынуждено чистить старшее поколение.
2. Длительность пауз. Сколько времени занимает каждая сборка, особенно Full GC. Длинные паузы — это и есть те «подтормаживания», которые видит пользователь: во время Stop-The-World (разбирали в 9.1) все потоки приложения стоят.
3. Заполнение кучи (occupancy) после Full GC. Это ключевой признак утечки. После полной сборки JVM освободила всё, что смогла. Если занятость кучи сразу после каждого Full GC монотонно растёт от сборки к сборке — значит, накапливаются объекты, которые GC не может удалить, потому что они достижимы. Это и есть картина утечки.

## Realtime-инструменты
#### **VisualVM и плагин VisualGC**  
Для полноценного анализа GC к VisualVM ставят плагин VisualGC (через Tools → Plugins). Без него VisualVM показывает кучу целиком, а VisualGC визуализирует её по поколениям: отдельно Eden, Survivor 0, Survivor 1, Old Generation и Metaspace — и то, как объекты перетекают между ними при сборках.  

**Практическая картина утечки в VisualGC выглядит так**: Eden наполняется и очищается Minor GC — это нормальный «пульс». А вот Old Generation растёт, растёт и растёт и не уменьшается даже после полных сборок. Это визуальное подтверждение того же, что видно в GC-логе: старшее поколение забивается тем, что GC не может собрать.
#### jcmd
консольная утилита, входящая в JDK и умеющая отправлять запущенной JVM диагностические команды. Это современный «единый вход» в диагностику из командной строки  
Работа начинается с получения PID процесса. Запуск jcmd без аргументов выводит список всех JVM-процессов с их идентификаторами:
```java
jcmd
```
Дальше команды отправляют по шаблону jcmd <pid> <команда>. Основные:
```java
jcmd <pid> GC.heap_info                  # сводка по куче: размеры и занятость поколений
jcmd <pid> GC.run                        # запросить сборку мусора (аналог System.gc())
jcmd <pid> Thread.print                  # дамп потоков со стектрейсами (как старый jstack)
jcmd <pid> GC.heap_dump /tmp/heap.hprof  # снять heap dump в файл (как старый jmap)
```
#### Heap dump и его анализ в Eclipse MAT
**Heap dump** — это снимок всей кучи в один момент времени: все объекты, их поля, значения примитивов и, главное, все ссылки между объектами. По сути это замороженный граф объектов JVM.  

**Eclipse Memory Analyzer (MAT)** - он открывает HPROF-дамп и позволяет строить гистограммы объектов, автоматически искать подозреваемых в утечке и прослеживать, кто и через что удерживает память.

#### JFR и JDK Mission Control
VisualVM и MAT покрывают realtime-картину и посмертный разбор снимка. Остаётся третий срез: что происходило с приложением во времени — как менялась память, когда случались паузы GC, где были всплески аллокаций и блокировок. Для этого есть Java Flight Recorder (JFR) — встроенный в JVM механизм записи событий.  
Ключевое свойство JFR — низкий overhead. Он спроектирован так, чтобы работать с минимальным влиянием на производительность, поэтому его можно включать в проде на работающем сервисе.  
Запись включается либо флагами при старте, либо командой jcmd <pid> JFR.start. Указывают имя файла и длительность:
```java
-XX:StartFlightRecording=filename=recording.jfr,duration=2m
```
Смотрят запись в JDK Mission Control (JMC) — официальном инструменте визуализации JFR-записей от Oracle. Он раскладывает бинарный .jfr в наглядные представления

**!! VisualVM даёт живую картину «прямо сейчас», MAT — статический снимок «в один момент», а JFR + JMC — историю во времени, разбор того, что происходило на протяжении интервала записи. Для утечки это ценно тем, что JFR-профиль аллокаций показывает, что именно и где усиленно создаётся, — то есть выводит не только на держателя памяти (это делает MAT), но и на код, который её порождает.**

### Методика поиска утечек
```java
Симптом (OOM / тормоза / рост памяти)
        │
        ▼
[1] Realtime: GC-лог / VisualVM  →  память растёт и не падает после Full GC?  → да, это утечка
        │
        ▼
[2] Heap dump  (jcmd GC.heap_dump  или  -XX:+HeapDumpOnOutOfMemoryError)
        │
        ▼
[3] MAT: Leak Suspects → retained heap → path to GC Root  →  класс-виновник и удерживающий GC Root
        │
        ▼
[4] (при необходимости) JFR + JMC: аллокации и паузы GC во времени  →  код-источник
```
