## Виртуальные потоки 
— лёгкие потоки, которыми управляет JVM, а не ОС.JVM мультиплексирует множество виртуальных потоков на небольшое число   
потоков-носителей (carrier threads — по умолчанию пул ForkJoinPool размером с число ядер). Это модель M:N (M виртуальных на N носителей).

1. Виртуальный поток выполняет код, будучи смонтированным (mounted) на носителе.
2. При блокирующем вызове (socket.read(), Thread.sleep(), JDBC и т. д.) JVM демонтирует (unmount) виртуальный поток: его стек сохраняется в куче, а носитель освобождается для другого виртуального потока.
3. Когда операция завершается, виртуальный поток снова монтируется на любой свободный носитель и продолжает с того же места.
```
Ключевая идея: блокировка виртуального потока не блокирует поток ОС. 
Поэтому «поток на запрос» снова становится жизнеспособной моделью — даже при миллионе одновременных соединений.
```
## Создание
```java
// 1. Один виртуальный поток «на лету»
Thread.startVirtualThread(() -> System.out.println("virtual"));

// 2. Builder API (можно задать имя, не запуская сразу)
Thread vt = Thread.ofVirtual().name("worker").start(() -> processRequest());

// 3. Главный рабочий инструмент: executor «один виртуальный поток на задачу»
try (ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor()) {
    Future<String> f = executor.submit(() -> fetchFromDb());
    String result = f.get();
} // try-with-resources закрывает executor: ждёт завершения всех задач
```
**newVirtualThreadPerTaskExecutor()** создаёт новый виртуальный поток на каждую задачу — и это правильно, их не нужно переиспользовать.

**Подходят** — I/O-bound нагрузка: HTTP-вызовы, JDBC, обращения к файловой системе, очереди. Классический сценарий — веб-сервер «поток на запрос»
**Не подходят** — CPU-bound вычисления: виртуальные потоки не ускоряют расчёты, число одновременно считающих потоков всё равно ограничено числом носителей (= числу ядер). Здесь нужен ForkJoinPool / parallel streams.

## Главные правила:
### 1. Не пулите виртуальные потоки. Они дёшевы; создавать новый на каждую задачу — правильно. Пул виртуальных потоков — антипаттерн, он искусственно ограничивает то, что и так бесплатно.

Иногда параллелизм нужно ограничить — но не из-за стоимости потоков, а из-за внешнего ресурса (пул JDBC-соединений, rate limit чужого API).  
Соблазн «взять newFixedThreadPool(N) на виртуальных потоках» — антипаттерн: фиксированный пул ограничивает число потоков,  
а нам нужно ограничить число одновременных обращений к ресурсу. Правильный инструмент — Semaphore.

### 2. Не используйте ThreadLocal для тяжёлых объектов. При миллионах потоков это миллионы копий. Применяйте ScopedValue.

ThreadLocal хранит изменяемую копию на каждый поток. При миллионах виртуальных потоков это миллионы копий,  
которые к тому же легко утекают. ScopedValue (финализирован в Java 25, JEP 506; preview с Java 21) — иммутабельный контекст,  
привязанный к участку выполнения, а не к потоку навсегда:

```java
static final ScopedValue<String> USER_ID = ScopedValue.newInstance();

// значение действует только внутри run()
ScopedValue.where(USER_ID, "alice").run(() -> {
    System.out.println(USER_ID.get()); // "alice"
    handleRequest();                   // вложенные вызовы тоже видят значение
});
// за пределами run() значение недоступно
```

### 3. Следите за pinning на блокирующих вызовах.

**Pinning** — ситуация, когда виртуальный поток не может демонтироваться от носителя при блокировке и держит его занятым.
Причины pinning в Java 21–23:
```java
// Java 21–23 — ПЛОХО: synchronized + блокирующий I/O = носитель прикреплён (pinned)
synchronized (lock) {
    data = Files.readAllBytes(path); // виртуальный поток не демонтируется → носитель занят
}

// РЕШЕНИЕ (Java 21–23): ReentrantLock демонтирует виртуальный поток при блокировке
private final ReentrantLock lock = new ReentrantLock();

lock.lock();
try {
    data = Files.readAllBytes(path); // виртуальный поток демонтируется → носитель свободен
} finally {
    lock.unlock();
}

Изменения в Java 24 (JEP 491). Pinning на synchronized устранён: виртуальный поток, заблокированный внутри synchronized, теперь корректно демонтируется.
```

### 4. Используйте Structured Concurrency вместо ручного управления группами задач.

Идея structured concurrency: если задача разбивается на параллельные подзадачи, то их время жизни ограничено блоком кода   
— как { } ограничивает область видимости переменных. Подзадачи запускаются и обязаны завершиться (или быть отменены)
внутри того же блока. Это исключает утечки потоков и «осиротевшие» задачи.

```java
21-24 java
// получить пользователя И его заказы параллельно; при ошибке любого — отменить остальных
try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
    Subtask<User>        user   = scope.fork(() -> fetchUser(id));
    Subtask<List<Order>> orders = scope.fork(() -> fetchOrders(id));

    scope.join();          // ждём обе подзадачи
    scope.throwIfFailed(); // если кто-то упал — пробрасываем исключение

    return new UserProfile(user.get(), orders.get());
} // выход из try-with-resources отменяет незавершённые подзадачи
```
В Java 25 API переработан: StructuredTaskScope стал sealed-интерфейсом, экземпляр открывается фабрикой open(...),  
а стратегией завершения управляет объект Joiner. Классы ShutdownOnFailure/ShutdownOnSuccess и метод throwIfFailed() удалены.

```java
// «все должны успешно завершиться, иначе исключение»
try (var scope = StructuredTaskScope.open(Joiner.<Object>awaitAllSuccessfulOrThrow())) {
    Subtask<User>        user   = scope.fork(() -> fetchUser(id));
    Subtask<List<Order>> orders = scope.fork(() -> fetchOrders(id));

    scope.join(); // ждёт всех; при первой ошибке отменяет остальных и бросает исключение

    return new UserProfile(user.get(), orders.get());
}
```
