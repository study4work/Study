## ThreadLocal
Это механизм, который позволяет создать изолированную копию переменной для каждого потока.

**Как это работает "под капотом"?**   
Данные хранятся внутри самого объекта Thread.
У каждого потока в Java есть специальное поле:  
```java
// Внутри класса java.lang.Thread
ThreadLocal.ThreadLocalMap threadLocals = null;
```
ThreadLocalMap — это хэш-таблица (похожая на HashMap), где:
* Ключ (Key): это сам экземпляр объекта ThreadLocal (используется как WeakReference).
* Значение (Value): это то, что ты туда положил (например, строка, объект пользователя и т.д.).
```java
Поток А (Thread A) ──> ThreadLocalMap ──> { Ключ: myThreadLocal, Значение: "Данные для А" }
Поток Б (Thread B) ──> ThreadLocalMap ──> { Ключ: myThreadLocal, Значение: "Данные для Б" }
```
Когда ты вызываешь myThreadLocal.get(), Java делает следующее:  
* Берет текущий выполняющийся поток (Thread.currentThread()).
* Залезает в его внутренний ThreadLocalMap.
* Ищет значение по ключу myThreadLocal.
* Возвращает его.  
Именно поэтому разные потоки получают разные значения, хотя обращаются к одному и тому же объекту ThreadLocal.

### Типичные сценарии
А. Избавление от синхронизации (State Isolation)  
Соединение с базой данных (JDBC Connection)  
Открывать новое соединение с БД (DriverManager.getConnection()) — это очень дорогая операция (сети, рукопожатия, аутентификация). Но использовать одно соединение на все потоки нельзя, потому что транзакции перемешаются (Поток А сделает commit, а Поток Б думал, что он еще в процессе).  
**Как это используется:**  
* Пришел запрос. Мы берем соединение из Пула и делаем DbContextHolder.setConnection(conn).
* Вызывается Controller -> Service -> Repository. В Repository мы просто делаем DbContextHolder.getConnection(). Нам не нужно передавать объект Connection через 10 методов в аргументах!
* Запрос завершен. Мы делаем DbContextHolder.clear(), и соединение возвращается в пул.  
Почему это работает: Каждый поток работает со своим собственным соединением. Нет конфликтов, нет очередей (synchronized), код остается чистым.
Б. Передача контекста сквозь слои приложения  
Представь веб-запрос. Тебе нужно знать ID текущего пользователя в Controller, затем в Service, затем в Repository. Передавать userId аргументом через 10 методов — ужасно.  
Вместо этого при входе запроса ты кладешь ID в ThreadLocal, а в любом месте кода просто делаешь UserContext.getUserId(). Поскольку весь запрос обрабатывается одним и тем же потоком, данные будут доступны везде.

### ГЛАВНАЯ ОПАСНОСТЬ: Утечка памяти (Memory Leak)
Почему происходит утечка?  
Вспомни структуру ThreadLocalMap. Она устроена хитро:
* Ключ (ThreadLocal) хранится как Слабая ссылка (WeakReference).
* Значение хранится как Сильная (обычная) ссылка (Strong Reference).
Сценарий катастрофы:
* Ты создал ThreadLocal и положил туда большой объект (например, список на 100 МБ).
* Переменная ThreadLocal в твоем коде вышла из области видимости и была удалена Сборщиком Мусора (Garbage Collector).
* Так как ключ в ThreadLocalMap был WeakReference, GC его удалил. Теперь в карте запись выглядит так: { null : БольшойОбъектНа100МБ }.
* НО! Сам поток (Thread) всё еще жив (особенно если это поток из Пула потоков / Thread Pool, которые живут вечно).
* Поток держит сильную ссылку на свою ThreadLocalMap, а она держит сильную ссылку на БольшойОбъектНа100МБ.
*Итог: GC никогда не сможет удалить этот объект, потому что на него есть сильная ссылка от живого потока. При каждом новом запросе в пул потоков будет добавляться еще 100 МБ "мертвого" мусора, пока приложение не упадет с OutOfMemoryError.
