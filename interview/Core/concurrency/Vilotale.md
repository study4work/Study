## У ключевого слова volatile есть две главные гарантии, которые оно дает потокам:
1. Видимость (Visibility): Если один поток изменил значение volatile переменной, это изменение мгновенно становится видимым для всех других потоков. (Значение не кэшируется в регистрах процессора конкретного потока, а всегда читается и пишется напрямую в основную память).
2. Запрет переупорядочивания (No Reordering):   Компилятор (JIT) и сам процессор (CPU) имеют право менять порядок выполнения инструкций местами для оптимизации скорости, если с точки зрения одного потока результат не меняется. volatile ставит "барьер памяти" (Memory Barrier), который запрещает переставлять операции чтения/записи этой переменной с другими операциями.

На примере Double-check locking 
### это проблема переупорядочивания
```java
public class SafeSingleton {
    private static volatile SafeSingleton instance;

    public static SafeSingleton getInstance() {
        if (instance == null) {                 // 1-я проверка без блокировки
            synchronized (SafeSingleton.class) {
                if (instance == null) {         // 2-я проверка под блокировкой
                    instance = new SafeSingleton();
                }
            }
        }
        return instance;
    }
}
```

Вся проблема кроется в этой, казалось бы, простой строке:
```java
instance = new SafeSingleton();
```

Для нас это одно действие. Но для JVM и процессора это три отдельные операции:
1. Выделить память под объект.
2. Вызвать конструктор и инициализировать объект (записать в него данные).
3. Присвоить ссылку на эту память переменной instance (сделать её не null).  
Нормальный порядок: 1 → 2 → 3  
Все хорошо. Объект создан, инициализирован, и только потом ссылка становится доступна другим.  
Переупорядоченный порядок (без volatile): 1 → 3 → 2  
Компилятор или процессор имеет полное право поменять местами шаги 2 и 3, потому что в однопоточной программе это ни на что не влияет. Это называется Instruction Reordering (переупорядочивание инструкций).  
А теперь представь сценарий с двумя потоками (Thread A и Thread B):
1. Thread A заходит в getInstance(). Видит, что instance == null.
2. Thread A захватывает synchronized и начинает выполнять new SafeSingleton().
3. Из-за оптимизации (переупорядочивания) Thread A выполняет Шаг 1 (выделил память) и Шаг 3 (присвоил ссылку переменной instance).  
⚠️ Внимание: В этот момент instance уже не равен null, но конструктор (Шаг 2) еще не вызван! Объект "пустой" и неинициализированный.  
4. В этот момент происходит переключение контекста. Thread A приостанавливается.  
5. Thread B заходит в getInstance().
6. Thread B делает первую проверку: if (instance == null).  
7. Поскольку Thread A уже присвоил ссылку (Шаг 3), эта проверка возвращает false!
8. Thread B полностью пропускает блок synchronized и сразу делает return instance;.  
💥 КАТАСТРОФА: Thread B получает ссылку на полуфабрикат. Если он попытается вызвать метод этого объекта, программа упадет (например, с NullPointerException или выдаст мусорные данные), потому что конструктор этого объекта еще не отработал.

Когда ты добавляешь volatile к переменной instance:  
Ты создаешь барьер памяти. Ты говоришь JVM:  
"Запрещаю тебе переставлять операцию присваивания ссылки (Шаг 3) выше операции инициализации объекта (Шаг 2). Объект должен быть полностью готов, прежде чем ссылка на него станет видна другим потокам".

Коherентность кэшей (Cache Coherence) — это фундаментальное аппаратное свойство современных многоядерных процессоров, которое гарантирует, что все ядра видят согласованную (одинаковую) картину данных в памяти, несмотря на то, что у каждого ядра есть свой собственный быстрый кэш (L1, L2).

**Проблема**: Зачем это вообще нужно?  
Представь архитектуру современного процессора:   
* Есть Оперативная память (RAM) — большая, но медленная.  
* Есть 4 Ядра (Cores) — быстрые.  
* У каждого ядра есть свой личный, сверхбыстрый кэш (L1/L2).  
**Сценарий без когерентности** (Хаос):  
Переменная x = 0 лежит в RAM.   
* Ядро 1 читает x. Оно копирует x = 0 в свой Кэш 1.  
* Ядро 2 читает x. Оно копирует x = 0 в свой Кэш 2.  
* Ядро 1 выполняет x++. В его Кэше 1 теперь x = 1. (Но в RAM всё еще 0, и в Кэше 2 всё еще 0).
* Ядро 2 читает x. Оно смотрит в свой Кэш 2 и видит 0.  
Итог: Два ядра работают с одной переменной, но видят разные значения. Программа ведет себя непредсказуемо. Это аппаратный уровень Data Race.
