## Escape Analysis 
это оптимизация JIT-компилятора JVM, которая анализирует, "вырывается" ли ссылка на объект за пределы метода или потока, в котором он создан.   
Если не вырывается — JVM применяет агрессивные оптимизации.

Создание объектов в Java кажется дешёвым, но на самом деле оно дорогое:  
* Аллокация в куче требует поиска свободного места и синхронизации в многопоточной среде.
* Сборка мусора (GC) останавливает все потоки (Stop-The-World) для очистки кучи.
* Синхронизация (synchronized) на локальных объектах бессмысленна, но JVM по умолчанию её выполняет.

Escape Analysis доказывает изолированность объекта и позволяет JVM легально убрать эти накладные расходы. 

#### Что конкретно делает (3 оптимизации)
1. Скалярная замена (Scalar Replacement)  
   Объект не создаётся вообще. Его поля превращаются в обычные локальные переменные или регистры CPU.
```java
// Было:
Point p = new Point(10, 20);
return p.x + p.y;

// Стало (в машинном коде):
int p_x = 10, p_y = 20;
return p_x + p_y;
```
Эффект: ноль аллокаций, ноль работы для GC.
2. Устранение синхронизации (Lock Elision)  
   Если объект не "сбегает", ни один другой поток не может к нему обратиться. Значит, synchronized на нём бессмысленен — JIT удаляет блокировки
```java
StringBuffer sb = new StringBuffer(); // внутри синхронизирован
sb.append("hello");
return sb.toString();
// JIT уберёт все мониторы, как если бы это был StringBuilder
```
Эффект: критично для многопоточных приложений.
3. Распределение в стеке (Stack Allocation)  
   Если скалярная замена невозможна, объект аллоцируется в стеке потока, а не в куче.
   Эффект: мгновенная аллокация (сдвиг указателя стека), мгновенная очистка (при выходе из метода), ноль нагрузки на GC.

### !.Важно
JIT-компилятор — это общий механизм, который превращает "горячий" байт-код в машинный код. Он делает множество оптимизаций.  
Escape Analysis — это одна из оптимизаций JIT, а не базовый механизм его работы. Без JIT (режим -Xint, только интерпретатор) EA не работает вообще.
