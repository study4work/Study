## Почему String immutable:
* Безопасность String Pool (Если бы строки были изменяемыми, изменение через одну ссылку сломало бы данные для всех остальных)
* Безопасность — строки используются для имён классов, URL, параметров соединений. Изменяемость позволила бы подменить значения.
* Потокобезопасность — неизменяемые объекты не нуждаются в синхронизации.
* String вычисляет хеш-код один раз при первом обращении и сохраняет результат в поле hash.   
  Все последующие вызовы hashCode() мгновенно возвращают сохранённое значение.  
  Это возможно только потому, что строка неизменяема — иначе кэш устаревал бы при каждом изменении содержимого.

```java
public final class String {
    private final byte[] value;  // Java 9+: байтовый массив (компактные строки)
    // до Java 8: private final char[] value;
    private int hash;
}
```
* Массив value — final, изменить ссылку нельзя.
* Сам массив не предоставляет публичных методов изменения.
* Все «изменяющие» методы (substring, replace, concat, toLowerCase и т.д.) возвращают новую строку.

## Метод Substring()
Извлекает часть строки (подстроку) от указанного начального индекса до конца строки или до указанного конечного индекса. Возвращает новый объект String.  
**До Java7** :  
создавал новый объект String, который разделял тот же самый внутренний массив char[] с исходной строкой.   
Новый объект просто имел свои собственные поля offset (смещение) и count (длина), указывающие на нужную часть общего массива.  
Работал быстро, но приводил к утечкам памяти.  
**С Java 7**:
Начиная с Java 7, substring() стал копировать нужные символы в совершенно новый массив char[]  
**Причина**:  
Если разработчик брал крошечную подстроку (например, 10 символов) от огромной строки (например, на 10 МБ, прочитанной из файла),  
то из-за общего массива char[] вся огромная строка оставалась в памяти, пока жила эта маленькая подстрока.  
Сборщик мусора (GC) не мог очистить оригинальную строку, что приводило к неожиданному OutOfMemoryError.

## Особенность метода replace() vs replaceAll()  
Оба метода заменяют ВСЕ вхождения, а не одно. Разница только в том, что именно они ищут.  
**replace()** - Ищет литерал. Пример: "a.b.c".replace(".", "-") вернет "a-b-c".
**replaceAll()** - Ищет совпадения по регулярному выражению. "a.b.c".replaceAll(".", "-") вернет "-----"  
(. в regex = любой символ, нужно экранировать \\.)

## String encoding  
Это набор правил, который сопоставляет символы (буквы, цифры, иероглифы) с числами (байтами)  
Внутри JVM: Объект String в Java всегда хранится в памяти в виде последовательности символов.  
До Java 9 это был массив char[] в кодировке UTF-16 (каждый символ занимал 2 или 4 байта).  
С Java 9 внедрены Compact Strings: если строка состоит только из латиницы, она хранится в byte[] (кодировка Latin-1, 1 байт на символ), что экономит память.  
Когда вы конвертируете String в байты (getBytes()) или создаете String из байтов (new String(byte[])), вы обязаны указывать кодировку (например, StandardCharsets.UTF_8).  
Если вы не укажете кодировку явно, Java использует дефолтную кодировку ОС.

## Сколько памяти занимает String  
Теоретически можно посчитать вручную. Память складывается из самого объекта String и его внутреннего массива.  
Объект String: Заголовок объекта (12 или 16 байт) + ссылка на массив (4 или 8 байт) + hash (4 байта) + coder (1 байт, с Java 9) + выравнивание (padding). Итого около 24–40 байт.  
Внутренний массив (byte[] или char[]): Заголовок массива (16 байт) + длина (4 байта) + сами данные (1 байт на символ для Latin-1 или 2 байта для UTF-16) + выравнивание.

## String deduplication в G1 GC  
Это механизм автоматического удаления дубликатов строк из кучи (Heap) на этапе работы сборщика мусора.  
В отличие от String Pool (который работает с литералами и методом .intern()), дедупликация работает с любыми объектами String в куче.  
Когда G1 GC сканирует память, он вычисляет хеши строк. Если он находит два разных объекта String, у которых содержимое идентично (равны по .equals()),  
GC оставляет только один объект, а все ссылки на второй объект перенаправляет на первый. Внутренний массив второго объекта удаляется.

Отключено по умолчанию  
Происходит асинхронно, во время циклов сборки мусора, не останавливая приложение  
Отлично экономит память в приложениях, которые загружают и обрабатывают огромные объемы текстовых данных  

## Почему String implements Comparable и CharSequence  
**CharSequence** — это общий интерфейс для любой последовательности символов (его также реализуют StringBuilder, StringBuffer, CharBuffer).  
Реализуя его, String позволяет использовать себя в API, которые принимают любую символьную последовательность.
Пример: Методы вроде Pattern.compile(CharSequence) или String.contentEquals(CharSequence) могут принимать на вход String, StringBuilder   

**Comparable<String>** - Этот интерфейс задает «естественный порядок» сортировки объектов. У строк естественным порядком  
является лексикографическое сравнение (по значениям Unicode символов).  
Пример: Благодаря этому String можно «из коробки» использовать в сортированных коллекциях (TreeSet, TreeMap)   
и сортировать через Collections.sort(list) или Arrays.sort(array) без необходимости писать и передавать кастомный Comparator.
